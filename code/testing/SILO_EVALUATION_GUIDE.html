What Silo is

Silo is a place where a small team keeps its little web apps. You upload an app as a .zip, and Silo runs it, so anyone with the link can open it. Your teammates can edit its code with you live in the browser, like Google Docs for code. Every version is also checked for security risks before anyone trusts it.

Think of it as three rooms in one building:

App Room

The app's home. It shows the live app, its version history, who has access, and the button to upload a new version.

Workbench

The shared code editor. Several people type at once, see each other's cursors, preview the change and publish it as a new version.

Security track

A map of every version. It shows what each version can do (files, network, commands) and which risks it adds or fixes compared with the one before.

The problem it solves: when a team shares code by email or chat, people overwrite each other's work, nobody knows who still has access, and nobody checks whether a new version quietly started doing something dangerous. Silo makes all three visible.

How it works inside

Silo has three programs. The browser talks to two of them.

How two people can type at once

The Workbench uses a CRDT (library: Yjs). Each typed character gets a permanent ID and remembers which character it was typed after. When two people type at the same spot, every computer applies the same tie-break rule, so everyone ends up with the same text in the same order. Nothing is overwritten and nothing is doubled. Edits are saved to the server, and the "Saved" pill only appears once the server has them. TC-01 tests exactly this.

How removing someone works

When you open the Workbench, the collab server checks your access. It then asks the API again for every open connection every 5 seconds. If you were removed, the server closes your connection, your editor turns read-only, your header says "Access changed — reload", and nothing you type afterwards reaches the server. TC-02 tests this.

How the Security track decides

  1. Read every file in the version: Python, JavaScript, HTML and the dependency lists.
  2. Silo's own rules. Python is parsed into a syntax tree (Python's ast module), so the rules see real calls, not just text. JavaScript and HTML are checked with patterns. Every file is searched for secret formats such as API keys.
  3. Semgrep runs its rules too. Where both flag the same line for the same weakness, one copy is kept.
  4. Capabilities are collected from the same pass: open(...) means it reads or writes files, subprocess means it runs commands, requests.get means it contacts other servers, and so on.
  5. Compare with the previous version: capabilities gained or lost, findings new or fixed, dependencies changed. Gaining anything makes the version Expanding, and only losing things makes it Reducing.
  6. Score the version from 0 to 100 and draw it on the map.

How we tested

We wrote the four test cases ourselves, filled in the course template (Silo_Test_Cases.pdf), and ran them as automated browser tests, so every run follows the exact same steps and keeps its own evidence.

  • Tool: Playwright drives real Chrome windows. Tests that need two or three people open separate browser profiles, each with its own account.
  • Where: a separate test copy of Silo (web on port 3100, API on port 8100) with its own SQLite database, so real data is never touched. Each test makes fresh accounts and a fresh app.
  • Evidence: after every step the test saves a screenshot and writes what it expected, what actually happened and pass or fail to result.json.
  • Two runs: results/before-fix/ is the first run, and results/after-fix/ is the run after the TC-04 change.
We designed TC-04 to fail. A test plan that only passes proves little. We picked a case we expected Silo to miss, recorded the failure, improved the analyzer, and showed the same test passing. That before and after is the improvement this evaluation demonstrates.

The four test cases

TC-01 · Workbench

Two users type on the same line at once

Pass
Goal
Two people type on the same line in the same instant. Both edits must survive, exactly once, in the same order on both screens.
Why it is hard
The two edits arrive milliseconds apart at the same position. A simple editor would overwrite one, duplicate one, or show "Saved" before the server has it.
What we did
Alex (Owner) and Morgan (Editor, joined by invite) open index.html. Both put the cursor at the end and type at the same moment: <!-- Alex edited --> and <!-- Morgan edited -->. Then Morgan reloads.
What happened
Both returned to Saved with no errors. Both editors showed identical text with each line once. Both lines survived the reload, and the server's stored draft (revision 3) held each line once.
TC-02 · Access

Editor removed while still connected

Pass
Goal
When the Owner removes an Editor, that person loses access within seconds, even on the page they already have open.
Why it is hard
The Editor's live connection was approved before the removal. If access were only checked at sign-in, they could keep typing.
What we did
Morgan joins by invite link and opens the editor. Alex removes Morgan from Share. Morgan tries to type, then reloads. Alex revokes the invite links, and a third account, Sam, tries the old link.
What happened
"Access changed — reload" appeared after 1.3 s (target 5 s). The editor turned read-only, and the typed text never reached the server. After reloading, Morgan saw "App not found" and the API answered 404. Sam saw "Invitation not found", and the Owner was the only member left.
TC-03 · Security track

Risky update, then a fix

Pass
Goal
Silo spots every risk a normal-looking update adds, labels it correctly, then recognises the fix.
Why it is hard
Ten different risks are spread over Python, an HTML template and JavaScript. Silo also has to get the direction right: Expanding for the update, Reducing for the fix.
What we did
Uploaded three versions of an "Expense notes" app. v1 is clean. v2 plants ten risks: a hard-coded API key, SQL built from strings, shell=True, pickle, TLS checks off, debug mode, innerHTML, a token in localStorage, a CDN script without an integrity check and a request with no timeout. v3 fixes all ten.
What happened
v1 is the origin (risk 2, 0 findings). v2 is Expanding with risk 76 and exactly 10 findings: 4 high, 5 medium, 1 low. Each has a file, line, CWE and fix, and the key's value is masked. v3 is Reducing with risk 13 and 0 findings, and all 10 are listed as fixed.
TC-04 · Security track

Shell command hidden behind dynamic imports

Fail → Pass
Goal
Silo still finds command execution when the code is written to hide it, as an attacker or a careless AI-written app might.
Why it is hard
Scanners usually look for names such as subprocess.run or os.system. This code reaches the same functions without writing those names.
What we did
v1 is clean. v2 adds one hidden admin route that runs whatever command is in the URL, four different ways:
@app.get("/admin/run")
def admin_run():
    cmd = request.args["cmd"]
41  mod = importlib.import_module("sub" + "process")  # module name built from pieces
42  getattr(mod, "run")(cmd, shell=True)              # function looked up by name
43  __import__("os").system(cmd)                      # import inside the call
44  sp.Popen(cmd, shell=True)                         # module renamed on import
First run
Fail. Risk 12, 1 finding. Only Semgrep caught line 44. Lines 41, 42 and 43 were missed, and the label did not say "Runs system commands". The app looked almost as safe as v1: a false negative, the most dangerous kind of miss.
After the fix
Pass. Risk 41, 4 findings. Lines 42, 43 and 44 each have a high CWE-78 finding, line 41 is flagged as a hidden import of subprocess, and the label lists "Runs system commands".

What we changed so TC-04 passes

Why it failed. Silo's Python rules matched a call by the name written in the code. If the code said subprocess.run, it was caught. The hidden route reached the same function under other names, so the rules never saw it.

The idea of the fix is like recognising a person by who they are rather than by the nickname they use today. Before the rules run, a small new step called the name resolver (_Names in apps/api/silo_api/services/security.py) works out what each name really points to:

DisguiseExampleThe resolver reads it as
Renamed importimport subprocess as sp → sp.Popensubprocess.Popen
Imported functionfrom os import system → system(cmd)os.system
Name built from piecesimportlib.import_module("sub" + "process")the module subprocess (it also joins f-strings and "".join([...]))
Import inside the call__import__("os").systemos.system
Lookup by namegetattr(mod, "run")subprocess.run

Once a name is resolved, the existing rules work unchanged: subprocess.run(..., shell=True) is a high CWE-78 finding, and the app gains the "Runs system commands" capability. Three smaller changes go with it:

  • Building a module name from pieces is itself reported (medium, CWE-470), because it hides what the app loads. A plain import_module("json") is not reported.
  • If the name cannot be worked out at all, for example when it comes from user input, Silo also marks the app as possibly running commands, so it fails safe.
  • os.system with a command built at run time is now high instead of medium, because that is where injection happens.

To avoid false alarms, the resolver only rewrites names that land in risky modules (subprocess, os, pty, pickle, marshal, builtins). Ordinary code such as request.args.get after from flask import request is read as before.

How we know nothing else broke

  • Two new regression tests in apps/api/tests/test_security.py: one checks all four disguises plus from os import popen, the other checks that ordinary imports are left alone.
  • All 112 API tests and all 9 browser tests pass, and the code style check is clean.
  • TC-01, TC-02 and TC-03 were rerun after the change and gave the same results. TC-03's numbers are identical (76 → 13, 10 fixed).

Questions you may be asked

Why are these good test cases, not easy ones?
Each targets a promise that is hard to keep: a race between two people, an already-open connection, ten mixed risks with the right direction, and code built to fool scanners. Each one checks the server's stored data, not only what the screen shows.
Why did you want a test to fail?
To find a real weakness and show the improvement. TC-04 failed, the analyzer was improved, a regression test now protects the fix, and the same test passes.
Is the TC-04 fix complete security?
No. It catches the common disguises. Code can still hide a call in ways only running the code would reveal, such as decoding the name from base64. For that case Silo fails safe and marks the app as possibly running commands. Static analysis narrows risk; it does not prove safety.
What are black-box and white-box here?
TC-01 and TC-02 are black-box: they act only through the browser, like a user. TC-03 and TC-04 also use white-box knowledge (we planted known risks on known lines) to check that each one is found exactly.
What is a regression test?
A test that keeps a fixed bug fixed. If someone later breaks the name resolver, test_commands_hidden_behind_aliases_and_dynamic_imports_are_found fails at once.
Why 1.3 seconds in TC-02 when the check runs every 5 seconds?
The check runs on a fixed 5-second cycle for every connection, and the removal happened 1.3 s before the next one (1.6 s in the second run). The worst case is about 5 seconds plus one API call, which is why the target is 5 s and the test's hard limit is 15 s.
