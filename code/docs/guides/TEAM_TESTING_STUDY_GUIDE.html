Understand Silo.
Then test it.

This guide is for a testing team that has not used Silo before. It explains the product in plain language and turns the evaluation into four clear end-to-end test cases.

1. What is Silo?

Silo is a shared workspace for small software projects. A person uploads an app, sees its versions and build logs, then invites teammates to work on the app's code together.

Dashboard

The home page. It lists apps, their latest version and recent activity. Start by creating or opening an app here.

App Room

The app's control room. Upload versions, look at build logs and open the preview of a running app.

Workbench

The shared editing space. Team members edit source files, comment, save checkpoints, preview a change and publish a version.

1. Upload
Put an app into Silo.
→
2. Open Workbench
See the app's source files.
→
3. Collaborate
Edit, comment, preview, publish.
The important rule: editing a shared draft does not immediately change the live app. A team first creates a preview from saved code, then deliberately publishes that version.

2. The few words to know

WordMeaning in Silo
AppA software project stored in Silo.
DraftThe editable shared copy of the app's files. It is not automatically live.
Version / releaseA frozen snapshot of code. It can be previewed and then published.
SavedThe change has been stored by Silo. Testers should wait for this state before their next important step.
CheckpointA named safety snapshot of the draft that can be restored later.
Owner / Editor / ViewerThe owner manages sharing and publishing; an editor changes code; a viewer can only look.
Security trackThe evaluation screen that compares versions and reports risky code patterns, capability changes and a risk score.

3. Before testing

Use the test copy

Do not use the main Silo database. The test copy has its own database and local password accounts.

http://localhost:3100/auth/local

Use separate browsers

For two people, use two browser profiles or one normal browser and one private window. Each person needs a different account.

Keep evidence

For every case, write Pass or Fail, note what happened, and take a screenshot of the key result.

Start the isolated test copy

apps/api/.venv/Scripts/python.exe scripts/dev.py --local --web-port 3100 --api-port 8100 --collab-port 1334

Then open http://localhost:3100/auth/local. Create the accounts described in the preconditions for each test.

About TC-03 and TC-04: these evaluate the Security track and require Semgrep plus the supplied security-demo ZIP files. TC-04 is intentionally a known-gap test: it is expected to fail before the planned analyzer improvement.

4. The four test cases

Each case is end-to-end: use the real screens as a user would, then check the result.

TC-01

Two people type on the same line

Tests whether shared editing merges simultaneous changes and keeps them after a reload.

Expected: pass

Set up

  • Create Owner and Editor accounts in separate browsers.
  • Upload tests/fixtures/counter.zip.
  • Invite the Editor with the Editor role.

Test text

Owner: <!-- Alex edited -->
Editor: <!-- Morgan edited -->

Steps

  1. Both open the same app's Workbench and wait for Saved.
  2. Both open Files, select index.html, and put the cursor at the end of the same last line.
  3. Both type their text at nearly the same time.
  4. Wait until both headers return to Saved.
  5. Reload the Editor's page and open index.html again.

Pass when

  • Both texts appear once in both editors.
  • Both people see the same final file.
  • The status goes from Saving to Saved without an error.
  • The texts remain after reload.
TC-02

Remove an editor who is already connected

Tests whether taking away access also stops a person whose Workbench is already open.

Expected: pass

Set up

  • Owner and Editor accounts in separate browsers.
  • Editor joined with an invite and has Workbench open.
  • Both see Saved.

Why it matters

A system must not only block a later login. It must stop the already-open editing session too.

Steps

  1. Owner opens Share.
  2. Owner removes the Editor by clicking the × next to their name.
  3. Watch the Editor's header for up to 15 seconds.
  4. Editor tries to type in the open file.
  5. Editor reloads Workbench.
  6. Owner revokes invite links. A third account tries the old invite link.

Pass when

  • Editor sees Access changed — reload and the editor becomes read-only.
  • Text typed after removal is never saved or visible to Owner.
  • After reload, the removed Editor cannot open the draft.
  • The old invite link says it is not found.
TC-03

Risky update, then a fix

Tests whether the Security track explains what changed and recognises a later fix.

Expected: pass

Set up

  • Semgrep is installed and Security track is available.
  • Use security-demo/expense-notes-v1.zip (clean) and expense-notes-v2.zip (risky).
  • Prepare v3 by fixing v2 as listed below.

Make v3 safer

Use safe command arguments, parameterised SQL, environment variables for keys, JSON instead of pickle, normal TLS/debug settings, textContent, no token storage, and a CDN integrity attribute.

Steps

  1. Upload v1, v2 and v3 to the same app.
  2. Open Security track.
  3. Open each version's panel.
  4. Check the capability matrix and risk chart.

Pass when

VersionExpected result
v1Origin, low risk, no findings.
v2Expanding, high risk, 10 findings: 4 high, 5 medium, 1 low.
v3Reducing, risk near v1, fixed findings shown.

The secret value must be hidden. Every finding should show a file, line, CWE and suggested fix.

TC-04

Command execution hidden by dynamic imports

Tests a deliberately difficult security case where dangerous code avoids obvious function names.

Expected today: known gap

Set up

Use the clean v1 security-demo app. Make v2 by adding the hidden command route from the evaluation notes.

What is being hidden?

mod = importlib.import_module("sub" + "process")
getattr(mod, "run")(cmd, shell=True)
__import__("os").system(cmd)
sp.Popen(cmd, shell=True)

All four lines can run a system command. The code is written to make simple pattern matching miss it.

Steps

  1. Upload clean v1, then hidden-command v2.
  2. Open Security track and click v2.

Correct future result

  • The arrow into v2 is Expanding.
  • v2 gains Runs system commands.
  • There is at least one high CWE-78 command injection finding.
  • The risk score is clearly higher than v1.

Expected result today

Fail is the honest expected result. The current direct-name rules may miss the dynamic import, getattr lookup and inline __import__. Record this as a false negative and use it to prove the analyzer improvement.

Final checklist

  • Used the isolated test copy on port 3100.
  • Used separate accounts and browser sessions.
  • Waited for Saved before major steps.
  • Recorded the actual result, not just the expected result.
  • Took screenshots of important states.
  • Marked TC-04 as a known gap before improvement.
  • Included browser console errors, if any.
