Workbench and Security track

Silo is "Google Docs for small software": you upload a small app, Silo runs it, and your team works on it together. This guide explains two of its pages simply.

App RoomThe running app, its versions and build logs.
WorkbenchWhere the team edits the app's code together, live.
Security trackWhat each version can do, and how each change affected security.

Workbench: what you can do

The Workbench is a shared code editor plus a live preview of the app. Everyone with access sees the same draft and each other's typing.

Part of the screenWhat it does
HeaderApp name, a status pill (Saved, Saving, Offline), who is online, Share, Security, Push update
Left tool railOpens drawers: Files, Changes, Versions, Comments, Build details
Centre stageThe app preview, or the code editor when you click Edit files
Right panelTeam chat and the AI collaborator: Send for a message, Ask Gemini for a code change

The main features

  1. Share: the owner creates an invite link with a role: viewer, commenter or editor.
  2. Edit together: two people can type in the same file at once; their changes merge.
  3. Comments: discuss a file or a selected piece of code; reply, resolve, reopen.
  4. Checkpoints: save a named snapshot of the draft and restore it later.
  5. Ask AI: Gemini proposes a change as a diff; you review it before it is applied.
  6. Build preview: freezes the saved draft and runs it, so you test exactly that version.
  7. Push update: save the draft as a new version, or publish it as the live app.

Workbench: how it works underneath

An edit is only confirmed once it is stored, so a crash never loses text that showed "Saved".

  • Live merging. The editor (CodeMirror) uses Yjs, a CRDT: a data structure that merges simultaneous edits from several people in the same order for everyone.
  • Permissions. Every save is rechecked against the person's role. Open connections are rechecked every 5 seconds, so removing someone takes effect almost at once.
  • Versions stay safe. Editing the draft never changes the live app. Only Publish does, and only after Build preview has tested that exact snapshot.
  • Conflicts. If two people publish at once, the second is refused until they reload. An AI change is refused if the draft changed after the AI read it.

Security track: what you can see

The Security track shows every build of an app as a graph, so you can see when the app gained new powers or new problems.

Expanding: more access or new problems Reducing No change
  • Build nodes: one per version, joined by arrows. Each shows a risk ring (0 to 100, lower is better) and its findings, access and dependency counts.
  • Arrows: say what the next build did; an expanding arrow is orange and animated.
  • Child nodes: under each build, its new findings (worst first) and the access it gained. Click one to jump straight to it.
  • Side panel: opens when you click a build.
    • Origin build (the first one): opens on its nutrition label, the "Capability Facts" card.
    • Later builds: open on Changes vs the previous build: a verdict sentence, access gained or lost, dependency changes, and file diffs.
    • Findings tab: each finding with its file and line, the code, why it matters, how to fix it, and Fix with AI.
  • Compare two builds: compare any two versions, not just neighbours.
  • Capability matrix: a grid of capability against build, with a ring where each kind of access first appeared.
  • Risk by build: bars of findings by severity, with the risk score as a line.

The nutrition label

A food label for code. What it can do lists the app's capabilities: network access (with hosts), reading and writing files, running system commands, environment variables and secrets, databases, scripts from other sites, browser storage, and camera or location. Ingredients lists its dependencies.

Security track: how the analysis works

The analysis is static and rule-based: it reads the source code without running it, and no AI decides what is risky.

  • Two rule engines. Semgrep (an open-source code scanner) runs Silo's rule file. Silo's built-in rules always run as well, reading Python's code structure (its syntax tree) and matching patterns in JavaScript and HTML.
  • What the rules catch. Examples: a shell command with shell=True, SQL built from strings, eval, loading pickled data, certificate checks turned off, debug mode, secrets in the code, innerHTML, remote scripts without an integrity check, tokens in browser storage. Each finding carries a CWE number, the standard ID for that weakness type.
  • Risk score. High findings add 10, medium 4, low 1, plus a little for risky access such as running commands. It is capped at 100.
  • Classification. Each build is compared with the previous one. It is expanding if it gains access, dependencies or medium or high findings; reducing if it only loses them or fixes findings; otherwise no change.
  • Speed. Semgrep scans every build in one run, and the results are cached on disk.

Honest limit: static analysis describes what the code can do. It does not prove the app is safe.

How the two pages connect: Fix with AI

The Security track finds the problem, and the Workbench is where it gets fixed. The fix shows up on the next build node, so you can see the loop close.

Likely questions

Can two people edit the same line at once?
Yes. Yjs merges both edits, and "Saved" shows only after the database has stored them.
What stops a viewer from editing?
Every save is rechecked on the server, and open connections are rechecked every 5 seconds.
Does the AI change code by itself?
No. It proposes a diff, a person applies it, and a stale proposal is refused.
Why rules and not AI for security?
Rules give the same answer every time and can be explained line by line.
What does "Expanding" mean?
The build can reach more, or has new medium or high findings, so it needs review.
Does a risk score of 0 mean the app is safe?
No. No rule matched, but static analysis cannot prove safety.
